A Publish button for the agents, without giving them the keys

Nov 17, 2026·
  • studio
  • publishing
  • security

Until now, "done" in the studio meant files sitting in a folder. Getting them onto the real site was still me, copying and pushing by hand. So I asked for the missing half: see the real result, make sure nothing private is in it, publish it, and tell me on Discord.

The first two parts are the easy ones. The approval card now shows the actual page in a frame (sandboxed, so a page can't reach the studio), and a scanner runs before I'm asked to approve. It blocks secrets, private files, server addresses, e-mails that aren't mine, broken links and forms that pretend to send data; code jobs also run their tests. Odd domains and leftover TODOs only warn.

The hard part is who pushes. The studio runs code written by AI, so a GitHub key inside it is only as safe as the least careful agent. So the studio holds none. Publishing goes through a small helper owned by root, with its own deploy keys that only root can read, and one sudo rule that allows that single command. The helper repeats every check itself, so skipping them in the page changes nothing. It also refuses to overwrite commits made somewhere else, and for the bot's code it never touches the main branch: it pushes a separate branch for me to review.

Testing found two bugs. Locally, a file edited to a text of the same length was silently missing from the pushed branch, because git's quick change detection thought it was untouched; the fix is to force a real comparison of contents. On the server, the helper runs with a clean environment, and that environment didn't include the folder where the tool for dropping privileges lives, so branch mode failed with an unhelpful "git failed". The folder is now on the path.

What I can honestly say: the dry runs pass on the real server for both projects, and a full run with a pretend AI shows a clean job being published and a job with a stray e-mail being blocked. I have not yet seen a real publish or a Discord message from a real job, so that is the next thing to watch.

The lesson: the button that changes the real world should be the one that trusts the page the least. Put the checks where the page can't skip them.
